---
title: Typed params from your API
description: Check your filter config against your list endpoint's params type.
---

By default `params` is inferred from your config, and each filter's value type
comes through on its own. Most of the time that's all you need.

If you have a typed API client, you can pass the endpoint's params type as a type
argument instead. You get autocomplete on keys, errors at compile time, and a
`params` typed as exactly your API type, so it can be passed straight to the
client:

```ts
interface ProductListParams {
  status: 'open' | 'closed' | null; // required, nullable
  sort: 'date' | 'price'; //           required, non-null
  search?: string | null; //           optional, nullable
  page: number; //     the hook owns the pagination keys,
  per_page: number; // so don't declare filters for them
}

const { params } = useFilters<ProductListParams>({
  status: f.select({ label: 'Status', valueType: 'string', options: statusOptions }),
  sort: f.select({
    label: 'Sort',
    valueType: 'string',
    options: sortOptions,
    defaultValue: 'date'
  }),
  search: f.text({ label: 'Search' })
});

productApi.getAll(params); // compiles
```

## What the type asks of your config

`P` is more than a list of value types. Its shape sets rules, and the compiler
checks them. Two questions decide what each param needs: is the key optional
(`?:`), and does the type allow `null`?

|                          | allows `null` (`X \| null`)              | no `null` (`X`)                                      |
| ------------------------ | ---------------------------------------- | ---------------------------------------------------- |
| **required** (`key: …`)  | needs a filter; `defaultValue` optional  | needs a filter **and** a `defaultValue`              |
| **optional** (`key?: …`) | filter optional; `defaultValue` optional | filter optional; if declared, needs a `defaultValue` |

The reasons:

- A required key always has a filter, so the key is always present in `params`.
- A param that can't be `null` always has a default, so an unset filter falls back
  to it instead of `null`.
- A param that allows `null` may stay unset.
- An optional key without a filter just doesn't appear in `params`.

Together these make `params` match `P` at runtime, which is why it can be typed as
exactly `P`.

<Callout>
  Unset filters are `null` at runtime, never `undefined`. If your API type says `search?: string`
  with no `null`, the hook could hand you a value the type claims can't happen. So the config must
  give that filter a `defaultValue`, or you declare the param as `string | null` if your API accepts
  an unset value.
</Callout>

The errors say what's missing. A required key without a filter reports
_"property `sort` is missing"_, and a filter without a needed default reports
_"property `defaultValue` is missing"_ on that filter.

## The same type in the loader

`<P>` works the same way on all three entry points:

```ts
// the hook
const { params } = useFilters<ProductListParams>(configs);

// the loader helper
const params = resolveFilterParams<ProductListParams>(configs, new URL(request.url).searchParams);

// or bind once for both, checked in one place
const productFilters = defineFilters<ProductListParams>(configs);
productFilters.useFilters(); // params: ProductListParams
productFilters.resolveFilterParams(new URL(request.url).searchParams); // params: ProductListParams
```

When a config is shared by the hook and a loader, put the type argument on
[`defineFilters<P>`](/docs/api/define-filters). It's checked once and both sides
get the same type.

## `satisfies`: checking without losing inference

Passing `<P>` turns off inference from your config. TypeScript can't infer some
type arguments while you supply others, so `params` comes from `P` rather than from
the config, and literal option types widen to whatever `P` declares. If you want
the check and the precise inferred types, check the config with `satisfies` and
let the hook infer:

```ts
import type { FiltersFor } from '@mbsatimov/use-filters';

const configs = {
  status: f.select({ label: 'Status', valueType: 'string', options: statusOptions }),
  sort: f.select({ label: 'Sort', valueType: 'string', options: sortOptions, defaultValue: 'date' })
} satisfies FiltersFor<ProductListParams>;

const { params } = useFilters(configs);
// params.sort: 'date' | 'price', inferred and non-null because it has a default.
// The config was still checked against ProductListParams.
```

Pick per screen: `<P>` when you want `params` shaped like the API type,
`satisfies FiltersFor<P>` when you want the check but the narrower inferred types.

<Callout type="warn" title="Using a custom createFilters? Bind FiltersFor first">
  `FiltersFor` is a standalone type and can't see your `createFilters` settings. On its own it
  assumes the default pagination keys (`page` / `per_page`) and `arrayFormat: 'array'`, so if you
  changed either, it checks against the wrong shape. Pass your settings as the second and third type
  arguments and export the result next to your factory:

```ts
// lib/filters.ts, next to your createFilters call
import type { FiltersFor as FiltersForBase } from '@mbsatimov/use-filters';

export type FiltersFor<P> = FiltersForBase<P, Record<'page' | 'page_size', number>, 'string'>;
```

Then import `FiltersFor` from your module. The functions from your factory
(`useFilters<P>`, `resolveFilterParams<P>`, `defineFilters<P>`) already know your
settings and don't need this.

</Callout>

## Array params sent as strings

With [`request.arrayFormat: 'string'`](/docs/api/create-filters#request), array
filters (`multiSelect`, `tags`, ranges) arrive in `params` as one joined string.
Declare those params as `string` in your API type:

```ts
interface ProductListParams {
  page: number;
  per_page: number;
  tags?: string | null; // f.multiSelect gives 'a,b'
}
```

`useFilters<P>` and `defineFilters<P>` from your factory know about this and
accept the `multiSelect`. A plain `satisfies FiltersFor<P>` doesn't, and reports
an error that looks like a library bug. Use the bound `FiltersFor` from the
callout above to fix it.
