Use these when the choices live on the server and are too many to load up front —
"pick a customer" out of thousands. Options are fetched via `loadOptions` as the
user types, one page at a time (start typing in the demo, or load more):

<AsyncDemo />

## `f.asyncSelect`

`loadOptions({ search, signal, cursor })` runs your server search and returns one
page: `{ options, nextCursor? }`. The `signal` lets you abort stale requests:

```ts
assignee: f.asyncSelect({
  label: 'Assignee',
  valueType: 'number',
  loadOptions: async ({ search, signal }) => {
    const users = await userApi.search({ q: search, limit: 20 }, { signal });
    return { options: users.map((u) => ({ value: u.id, label: u.name })) };
  }
});
```

No `nextCursor` means "this is everything" — see [Pagination](#pagination) to
load more.

The resolved filter gives you `loadOptions`, `selectedOption`, and
`onSelectOption(option | null)` to set or clear the choice.

## `f.asyncMultiSelect`

The multiple-choice variant. It exposes `selectedOptions`, `onToggleOption(option)`,
and `onSetOptions(list)`.

## Pagination

To let the user load more options, return a `nextCursor` with each page. The
**cursor** is a bookmark: a value that tells _your_ loader where the next page
starts. `useFilters` never looks inside it — it only hands it back:

1. The picker opens → `loadOptions` is called with `cursor: null` (first page).
2. You return `{ options, nextCursor: 2 }`.
3. The user scrolls to the bottom → `loadOptions` is called with `cursor: 2`.
4. On the last page you return `nextCursor: null` — there's nothing more to load.
5. A new search starts over at `cursor: null`.

For a page-number API, the cursor is just the next page:

```ts
customer: f.asyncSelect({
  label: 'Customer',
  valueType: 'number',
  loadOptions: async ({ search, signal, cursor }) => {
    const page = Number(cursor ?? 1);
    const res = await api.customers({ q: search, page, per_page: 20 }, { signal });
    return {
      options: res.results.map((c) => ({ value: c.id, label: c.name })),
      nextCursor: page * 20 < res.count ? page + 1 : null
    };
  }
});
```

For a cursor API (Stripe's `starting_after`, GraphQL's `after`, …), return the
token it gives you:

```ts
loadOptions: async ({ search, signal, cursor }) => {
  const res = await api.customers({ q: search, after: cursor ?? undefined }, { signal });
  return {
    options: res.items.map((c) => ({ value: c.id, label: c.name })),
    nextCursor: res.next // e.g. "abc123", or null on the last page
  };
};
```

A cursor is a `number | string`. The registry kits' `useAsyncOptions` hook
tracks the cursor for you and loads the next page when the list is scrolled to
the bottom (or "Load more" is picked with the keyboard). With TanStack Query,
the same loader drops straight into `useInfiniteQuery`:

```ts
useInfiniteQuery({
  queryKey: ['customers', search],
  initialPageParam: null as OptionsCursor | null,
  queryFn: ({ pageParam, signal }) => filter.loadOptions({ search, signal, cursor: pageParam }),
  getNextPageParam: (page) => page.nextCursor ?? undefined
});
```

<Callout>
  `loadOptions` isn't debounced by `useFilters` — debounce the **search input** in your UI
  (`searchDebounceMs` is the per-filter hint for how long; the registry hook defaults to 300 ms).
  That way a "load more" request is never delayed or merged with a search.
</Callout>

## The label sidecar

The URL stores only the chosen **id**. After a refresh there's nothing in memory to
turn that id back into a name — so async filters also store the selected label in a
companion param, `<key>_label`, and hand you the pair back ready to render:

```text
?assignee=42&assignee_label=Ada+Lovelace
```

You never manage this sidecar yourself; the option-aware handlers write the value
and label together. The `_label` params are display-only and never appear in the
`params` you send to your API.

<Callout type='warn'>
  Don't name a filter `something_label` — that suffix is reserved for the sidecar. A dev-mode
  warning fires if you do.
</Callout>

## Value types

`valueType` is **required** on every async filter — `'number'` for ids, `'string'`
for UUIDs/slugs. If it doesn't match what `loadOptions` actually returns, values
won't round-trip (e.g. string ids parsing back as `null`):

```ts
assignee: f.asyncSelect({ label: 'Assignee', valueType: 'string', loadOptions });
```

A dev-mode warning fires if `loadOptions` resolves options whose value type
doesn't match the declared `valueType`.

This same requirement applies to static `select` / `multiSelect`. Since a
choice filter's `options` are often **fetched at runtime**, the same config may
also be used somewhere the options aren't loaded — a
[route loader](/docs/guides/route-loaders) calling `resolveFilterParams`. Making
`valueType` required (rather than inferring it from `options`) means the hook
and the loader always agree on the URL's value type, whether or not `options`
happen to be loaded at that call site:

```ts
owner: f.select({
  label: 'Owner',
  valueType: 'number', // the static source of truth
  options: fetchedOwnerOptions // present in the component, empty in the loader
});
```

`valueType` is type-checked against your option values — a mismatched option is
a compile error on that option, not a silent runtime divergence.
