title: Introduction
description: Headless, URL-synced filter state for React. What it does and when to use it.
---

use-filters is a React hook for list and table screens. You describe your filters
in one object; it keeps their state in the URL and gives you a typed `params`
object to fetch with.

Doing this by hand usually means a `useState` per filter, your own URL parsing
and serializing, and remembering to go back to page 1 whenever a filter changes.
None of it is hard, but it is easy to get slightly wrong, and every screen ends up
with its own copy.

The library handles the state. It ships no components, so the controls are up to
you.

## A first look

```ts
const { params, filters } = useFilters({
  status: f.select({ label: 'Status', valueType: 'string', options: statusOptions }),
  search: f.text({ label: 'Search' })
});
```

The hook returns two things, and you use them in different places:

- `params` holds the current values plus pagination, e.g.
  `{ status, search, page, per_page }`. Send it to your API and use it as the cache
  key.
- `filters` is the same set of filters with a current `value` and an `onChange`
  on each, ready to render as whatever controls you like.

Both come from the URL query string. Change a filter and the URL changes; open a
URL and the filters are restored. [How it works](/docs/concepts/how-it-works)
covers this properly. Read it early.

## What it covers

It manages filter state, using [nuqs](https://nuqs.dev) for the URL. That
includes parsing, types, pagination, debounced and manual commits, and a helper
that computes the same `params` in a route loader.

It does not fetch data or render anything. Use whatever fetcher you already have
(React Query, SWR, `fetch`) and whatever controls you like. The only runtime
dependencies are the `react` and `nuqs` peers.

If you want the UI as well, there are [ready-made kits](/docs/ready-made-ui)
built on shadcn/ui that you copy into your project.

## When to use it

It fits when you have a filtered list or table and want some of these:

- filters in the URL, so links can be shared and refreshes and the back button work
- one typed object to drive fetching and caching
- pagination, debounced search and "Apply" panels handled the same way everywhere
- the same values computed in a route loader for server rendering

For one or two filters that don't need to be in the URL, plain `useState` is
simpler.
