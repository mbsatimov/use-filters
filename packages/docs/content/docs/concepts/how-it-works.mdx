title: How it works
description: 'The mental model: one config in, two outputs out, both read from the URL.'
---

The filter state lives in the URL. The hook reads it and gives your screen the two
things it needs: values to fetch with, and controls to render.

## One config, two outputs

You pass `useFilters` a config, a plain object describing your filters, and get
back two outputs that you use in different places:

```ts
const { params, filters } = useFilters({
  status: f.select({ label: 'Status', valueType: 'string', options: statusOptions }),
  search: f.text({ label: 'Search' })
});
```

- `params` is for data. It's a plain object of the applied values plus pagination,
  e.g. `{ status, search, page, per_page }`, ready to send to your API and use as a
  cache key.
- `filters` is for the UI. It's an array of resolved filters: each one is your
  config plus the current `value` and functions to change it. You render these
  yourself; the library has no components.

Both are read from the URL query string:

```text
                 ?status=open&search=acme&page=2
                               │
                          useFilters
                 ┌─────────────┴─────────────┐
        params (to fetch)            filters (to render)
       { status: 'open', … }     [ { value, onChange, … }, … ]
```

Since the state is in the URL, refreshing the page, the back button, bookmarks and
shared links keep working without any storage of your own. And because `params`
changes exactly when the URL does, it works as a cache key for React Query, SWR or
any other fetcher.

## One value, three places to read it

Each filter's value can be read in three places. Knowing which one to use covers
most of what trips people up:

| Read                    | to get                                       |
| ----------------------- | -------------------------------------------- |
| `filter.value`          | what the control shows right now (the draft) |
| `filter.committedValue` | what has been applied and written to the URL |
| `params.<key>`          | the same applied value, for fetching         |

For an ordinary filter all three are the same, because every change goes straight
to the URL. They only differ when a filter waits before committing, like a
debounced search box or a panel with an Apply button. Then `value` follows the
control while `committedValue` and `params` keep the last applied value.
[Values & commits](/docs/concepts/values-and-commits) explains this.

## The rest of the return value

- `filterMap` holds the same resolved filters keyed by name (`filterMap.status`),
  for when you want one filter rather than a loop. Unlike `filters`, it includes
  hidden ones.
- `isFiltered` and `isDirty` tell you whether anything differs from its default,
  and whether anything is waiting to be applied.
- `apply` and `cancel` commit or discard every pending change.
- `reset` sets every filter back to its default, waiting for Apply where a filter
  is manual. `instantReset` does the same but writes the URL immediately, which is
  what a "Clear all" button wants.
- `setFilter(key, value)` sets one filter from code.

`paramsStr`, `meta` and the exact types are in the [API reference](/docs/api/use-filters).
