By default a filter change is written to the URL immediately. That's right for a
select. For a search box it means a request per keystroke, and in a mobile sheet
nothing should change until the user taps Apply. The `commit` option controls
when a change is written. It's the one part of the library that takes a moment to
get used to.

## The three modes

Set `commit` on each filter:

| `commit`              | The control updates | `params` and the URL update                     |
| --------------------- | ------------------- | ----------------------------------------------- |
| `'instant'` (default) | immediately         | immediately                                     |
| `{ debounce: ms }`    | immediately         | `ms` after the last change (the timer restarts) |
| `'manual'`            | immediately         | when you call `apply()`                         |

The control always responds straight away. `useFilters` keeps a local draft, so
an input shows what you type even when nothing has been written yet. The mode only
decides when that draft is committed to the URL and `params`.

## Draft and committed values

That's why each filter has both `value` and `committedValue`
([see How it works](/docs/concepts/how-it-works#one-value-three-places-to-read-it)):

- `value` is the draft, what the control shows now.
- `committedValue` is what has been applied, and what `params` and the URL hold.

They're the same for instant filters and only differ while a change is waiting.

update as you type, but `params` and the URL only follow once the debounce

## Applying or discarding everything

When any filter has a change waiting, the hook tells you and gives you two actions
that act on all of them:

- `isDirty` is `true` while any change is waiting. It's always `false` if every
  filter is instant.
- `apply()` commits every waiting change now, including ones still mid-debounce.
- `cancel()` throws them away, and each filter goes back to its `committedValue`.

```tsx
const { isDirty, apply, cancel } = useFilters(configs);

<button disabled={!isDirty} onClick={apply}>Apply</button>
<button disabled={!isDirty} onClick={cancel}>Cancel</button>
```

`params` only ever holds committed values, so you can fetch with it directly. A
half-typed search never sends a request. [Apply panel](/docs/guides/apply-panel)
builds a full Apply/Cancel panel.

To clear everything, `reset()` sets every filter back to its default and still
waits for Apply on manual filters. `instantReset()` clears them and writes the URL
in one go, which is usually what a "Clear all" button wants.

## Per-filter actions

Each resolved filter has its own `isDirty`, `apply()` and `cancel()` for just that
filter, handy for a per-row "apply" or "undo". It also has `reset()`, which goes
back to the default and respects `commit`, and `instantReset()`, which ignores it.

## Setting a default mode

Instead of repeating `commit` on every filter, set a default for a call or for the
whole app. The most specific setting wins:

per-filter `commit` → `useFilters(…, { defaultCommit })` → `createFilters({ defaultCommit })` → `'instant'`

```tsx
// the whole app waits for Apply
export const { useFilters, f } = createFilters({ defaultCommit: 'manual' });

// one screen goes back to instant, and its search is debounced
useFilters(
  {
    q: f.text({ label: 'Search', commit: { debounce: 400 } }),
    status: f.select({ label: 'Status', valueType: 'string', options }) // instant
  },
  { defaultCommit: 'instant' }
);
```

<Callout>
  `commit` is not the same as nuqs's `limitUrlUpdates: debounce(ms)`. That one throttles how often
  the browser history is written after a value has been committed. `commit` decides whether the
  value is committed in the first place.
</Callout>
