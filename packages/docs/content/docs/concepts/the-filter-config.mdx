---
title: The filter config
description: 'A config is plain data built with f.*: value types, defaults, and hidden filters.'
---

The object you pass to `useFilters` is plain data. Each entry comes from an `f.*`
builder that records the filter's kind and options. Nothing renders and nothing
runs until the hook reads it.

```ts
const configs = {
  search: f.text({ label: 'Search' }),
  status: f.select({ label: 'Status', valueType: 'string', options: statusOptions }),
  min_price: f.number({ label: 'Min price' })
};
```

Since it's plain data, you can export it from a module,
[build it at runtime](/docs/guides/dynamic-filters) from an API response, or pass it
to a [route loader](/docs/guides/project-setup#3-route-loaders-with-resolvefilterparams).
The hook and the loader read the same object.

## Value types

The builder decides the type of the filter's value in `params`:

```ts
f.text(...)         // string | null
f.number(...)       // number | null
f.boolean(...)      // boolean | null
f.select(...)       // V | null       (V driven by valueType, checked against options)
f.multiSelect(...)  // V[] | null
```

For `select` and `multiSelect`, `V` comes from the required `valueType`
(`'number'` or `'string'`). Numeric options give `number | null`, a union of
strings gives `'open' | 'closed' | null`, and an option that doesn't match the
`valueType` is a compile error. See [Filter types](/docs/filter-types/overview)
for the full list.

<Callout>
  `valueType` is required instead of being inferred from `options` because a route loader calling
  `resolveFilterParams` never sees `options`. Declaring it means the loader and the hook parse the
  value the same way. See [Async filters](/docs/filter-types/async#value-types).
</Callout>

## Defaults

`defaultValue` is the value used when the URL has no param for the filter. A
filter at its default counts as inactive: `isFiltered` ignores it, and with
`clearOnDefault` (on by default) it isn't written to the URL at all:

```ts
status: f.select({
  label: 'Status',
  valueType: 'string',
  options: statusOptions,
  defaultValue: 'open'
});
// No `?status` in the URL → params.status is 'open', and isFiltered ignores it.
```

A filter with a default falls back to it when unset and when cleared, so it can't
be `null`, and its type drops the `| null`:

```ts
f.select({ label: 'Status', valueType: 'string', options });
// params.status: 'open' | 'closed' | null

f.select({ label: 'Status', valueType: 'string', options, defaultValue: 'open' });
// params.status: 'open' | 'closed'
```

That's true for every kind, in the hook and in
[`resolveFilterParams`](/docs/api/resolve-filter-params). You can still clear a
filter that has a default: clearing it, or calling `onChange(null)`, sets it back
to the default.

## Hidden filters

`hidden: true` keeps a filter in `params` and `filterMap` but leaves it out of the
`filters` array. Use it for a value you render somewhere other than the toolbar,
such as a search box in the header, or one you only set from code:

```ts
const { params, filters, filterMap } = useFilters({
  search: f.text({ label: 'Search', hidden: true }), // in params, not in `filters`
  status: f.select({ label: 'Status', valueType: 'string', options: statusOptions })
});
```

[Search, sort & placement](/docs/guides/search-sort-and-placement) covers putting
filters in different parts of the page.

## Shared per-filter options

Every kind accepts these:

| Option         | Purpose                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------- |
| `label`        | Required. Human label for the control.                                                    |
| `placeholder`  | Optional; defaults to `label`.                                                            |
| `defaultValue` | Value when the URL param is absent (above).                                               |
| `hidden`       | Keep in `params`, omit from `filters` (above).                                            |
| `commit`       | When a change reaches the URL. See [Values & commits](/docs/concepts/values-and-commits). |
| `meta`         | Your own typed UI hints. See [UI metadata](/docs/guides/ui-metadata).                     |
| `nuqs`         | Per-filter [nuqs options](https://nuqs.dev), e.g. `{ history: 'push' }`.                  |
